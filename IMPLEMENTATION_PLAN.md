## 1. Project Overview

### Description
Personal media knowledge graph and digital library. Manages movies, music, books, and sheet music — storing files in S3 and metadata/relationships in DynamoDB, with a React frontend built on AWS Amplify Gen 2.

### Goals
- Unified browsing of movies, music artists, recordings, and their relationships (knowledge graph)
- Digital library for books (PDF/epub) and sheet music (PDF) with S3 storage and searchable catalog
- Modern, maintainable frontend that Claude Code can operate and extend
- Single AWS account deployment with clean resource naming

### Success Criteria
- All 905 knowledge graph items imported and queryable via frontend
- 307 books and 112 sheet music files uploaded to S3 with metadata in DynamoDB
- All entity types browsable with list views, detail views, and relationship navigation
- Edit forms for entities (name, language, cast/performer links)
- Deployed and accessible via Amplify hosting

### Scope Boundaries
- **In scope**: Knowledge graph (movies/music), book catalog, sheet music catalog, S3 storage, Amplify frontend
- **Out of scope (future)**: Kindle library integration, full-text search, recommendations, public access
- **Not a backend API project**: Amplify Gen 2 provides the data layer (AppSync + DynamoDB) — no custom Lambda/API Gateway needed

### Components
| Component | Technology | Purpose |
|-----------|------------|---------|
| Frontend | React + TypeScript + Amplify UI | User interface |
| Data Layer | Amplify Data (AppSync + DynamoDB) | GraphQL API + database |
| Auth | Amplify Auth (Cognito) | User authentication |
| Storage | Amplify Storage (S3) | Book/sheet music file storage |
| Hosting | Amplify Hosting (CloudFront) | Web deployment |

### Data Flow
```
1. User authenticates via Cognito
2. Frontend queries AppSync GraphQL API (auto-generated by Amplify)
3. AppSync resolves against DynamoDB (knowledge_graph table)
4. For files (books, sheet music), frontend fetches from S3 via Amplify Storage
5. Edits go through AppSync mutations → DynamoDB
```

### Why Amplify Gen 2 (not CDK + Lambda + API GW)
The input materials (dynamo_implementation/WORKER_INSTRUCTIONS.md) specify Amplify Gen 2 with a complete data model. Amplify Gen 2:
- Provides DynamoDB + GraphQL API with zero Lambda code
- Manages its own CloudFormation stacks
- Includes auth, storage, hosting out of the box
- Single project structure (no multi-repo overhead)
- TypeScript-native backend definitions

## 3. Technical Specifications

### Data Schema — Media Catalog (from input/dynamo_implementation)

> **Note on naming**: The DynamoDB table is called `knowledge_graph` (from input materials). This is NOT a graph database — it's a standard DynamoDB single-table design where entities and their relationships are stored as rows, with GSIs enabling relational-style queries.

#### DynamoDB Table: `knowledge_graph`
| Attribute | Type | Role |
|-----------|------|------|
| `id` | String | **Partition key** — globally unique (`slug_hash` for entities, `entity___role___entity` for relationships) |
| `entity_type` | String | **Sort key** |

#### Entity Types
| Type | Count | Key Fields |
|------|-------|------------|
| `movie` | 94 | name, language (en/cs) |
| `person` | 231 | name, given_name, family_name, roles[] (actor/director/musician), language |
| `band` | 33 | name, language |
| `artist` | 3 | name, language (P!nk, Amy Winehouse, Dario G) |
| `collaboration` | 8 | name, language |
| `tag` | 5 | name, language (non-performer labels — hide from main nav) |
| `recording` | 94 | name, language |

#### Relationship Types
| Type | Count | Fields | Links |
|------|-------|--------|-------|
| `movie_cast` | 327 | role (actor/director), movie_id, movie_name, person_id, person_name | movie → person |
| `recording_performer` | 96 | recording_id, recording_name, performer_id, performer_name, performer_type | recording → performer |
| `recording_movie` | 14 | recording_id, recording_name, movie_id, movie_name | recording → movie (soundtracks) |

#### Global Secondary Indexes (6)
| GSI | Partition Key | Sort Key | Purpose |
|-----|---------------|----------|---------|
| byType | entity_type | name | List all entities of a type |
| byCastMovie | movie_id | role | Cast list for a movie |
| byPersonFilm | person_id | movie_name | Filmography for a person |
| byRecording | recording_id | performer_name | Who performs a recording |
| byPerformer | performer_id | recording_name | Discography for a band/artist |
| byLanguage | language | name | Filter by language |

### Data Schema — Extended (Books & Sheet Music)

#### New Entity Types (to add to knowledge_graph table)
| Type | Count | Key Fields |
|------|-------|------------|
| `book` | 307 | name, author, language, format (pdf/epub), s3_key |
| `sheet_music` | 112 | name, artist_name, language, s3_key |

#### New Relationship Type
| Type | Purpose | Fields |
|------|---------|--------|
| `sheet_music_performer` | Links sheet music to existing artist/band/person | sheet_music_id, performer_id, performer_name |

**Note**: Book metadata will be extracted from filenames (`{Title} by {Author}.{ext}`). Sheet music metadata from filenames (`{Artist} - {Song}.pdf`). Where artists overlap with existing knowledge graph entities (e.g., U2, Bob Dylan, Rolling Stones), relationships will be created.

### Amplify Data Model (from input/dynamo_implementation)

```typescript
const schema = a.schema({
  KnowledgeGraphItem: a.model({
    id: a.string().required(),
    entityType: a.string().required(),
    name: a.string(),
    language: a.string(),
    givenName: a.string(),
    familyName: a.string(),
    roles: a.string().array(),
    role: a.string(),
    movieId: a.string(),
    movieName: a.string(),
    personId: a.string(),
    personName: a.string(),
    recordingId: a.string(),
    recordingName: a.string(),
    performerId: a.string(),
    performerName: a.string(),
    performerType: a.string(),
    // Extended fields for books/sheet music
    author: a.string(),
    format: a.string(),
    s3Key: a.string(),
    artistName: a.string(),
    sheetMusicId: a.string(),
    updatedAt: a.datetime(),
    updatedBy: a.string(),
  })
  .identifier(['id', 'entityType'])
  .secondaryIndexes((index) => [
    index('entityType').sortKeys(['name']).name('byType'),
    index('movieId').sortKeys(['role']).name('byCastMovie'),
    index('personId').sortKeys(['movieName']).name('byPersonFilm'),
    index('recordingId').sortKeys(['performerName']).name('byRecording'),
    index('performerId').sortKeys(['recordingName']).name('byPerformer'),
    index('language').sortKeys(['name']).name('byLanguage'),
  ])
  .authorization((allow) => [allow.authenticated()]),
});
```

### S3 Storage Design

**Bucket**: `hyl-media-storage-{env}-{account}` (single bucket, partitioned by prefix)

```
hyl-media-storage/
├── library/                    # Books (307 files)
│   ├── {sanitized-filename}.pdf
│   └── {sanitized-filename}.epub
└── sheet-music/                # Sheet music (112 files)
    └── {sanitized-filename}.pdf
```

- File metadata (title, author, artist) stored in DynamoDB, not S3 metadata
- S3 key stored in DynamoDB `s3_key` field for retrieval
- Access via Amplify Storage (authenticated users only)

## 10. Dublin Core Metadata Model (Phase 15+)

A comprehensive refactor (Phases 15–18) makes hyl-media's metadata **byte-compatible** with the
Digital Horizon (DH) metadata-repository at `/home/ubuntu/digital-horizon-playbook`. The full
field-level mapping is in **`docs/dc-metadata-mapping.md`** (the authoritative spec); this section
summarizes the architecture.

### 10.1 Target store
A new DynamoDB table **`hyl-media-metadata-repository`**, schema-identical to DH:
- **PK** = `resourceId` (a deterministic UUIDv5-shaped id, `derivedArtifactId(legacyId, entityType)`)
- **SK** = `#{language_code}#{normalized_title}`
- **`Attributes`** map = DH's 28-field conformant-sidecar template (`dc_*` + `_*` + `s3_*`), plus
  hyl-media `_`-prefixed extensions (`_entity_kind`, `_legacy_id`, `_tags`, `_external_links`, …)
  for lossless round-trip.
- GSI `resource-account-index` on `resource_account` (registry key `hylm`).

**Created by the DH Python CLI** (`tools/metadata-repository create-table`), not Amplify — see the
Decision Log exception to Critical Rule #6.

### 10.2 Conformant format (NOT pure DC)
The contract is DH's **conformant sidecar** (`buildDublinCoreSidecar` in
`amplify/functions/recordings/_shared/metadata.ts`) — designed for Elasticsearch/Kendra, so field
names, prefixes, ordering, and S3 organization must match exactly, not just DC semantics. The
faithful port lives in `scripts/lib/build-dc-sidecar.mjs`. The legacy auto-generated
`docs/metadata-repository.md` table-doc shape is **superseded** and not the target.

### 10.3 S3 organization (must match DH)
```
<bucket>/<category>/<uuid>/<filename>                        ← content artifact
<bucket>/metadata/<category>/<uuid>/<filename>.metadata.json ← Dublin Core sidecar
```
`<category>` ∈ {`audio`, `datasets`, `documents`}. hyl-media: books/sheet_music PDFs → `documents`;
JSON descriptors for non-file entities → `datasets`. Implemented in `scripts/lib/dc-paths.mjs`.

### 10.4 Entity & relationship mapping
- `dc_type` (DCMI): movie→`MovingImage`, recording→`Sound`, book/sheet_music→`Text`,
  person/band/collaboration→`Dataset` (agents; true kind in `_entity_kind`).
- Relationships collapse into DC terms — `recording_performer`/`sheet_music_performer`/book author
  → `dc_creator`; `movie_cast` director→`dc_creator`, actor→`dc_contributor`; `recording_movie`
  → `dc_is_part_of`/`dc_has_part`; reverse edges → `dc_relation`. The 3–4 cross-ref item types
  retire after migration → one source of truth. Implemented in `scripts/lib/entity-to-dc.mjs`.

### 10.5 Sync pipeline
Producers emit S3 sidecars; the reused DH Python CLI (`update-metadata`) scans the registered
bucket and upserts to the table (`overwrite_by_pkeys=['PK','SK']`). hyl-media's bucket is added to
the CLI's bucket registry (`resource_account=hylm`).

### 10.6 Roadmap
- **Phase 15** — design + foundation (mapping spec, vocab, builder/resolver, table, dry-run audit). ✅
- **Phase 16** — migration: emit descriptors + sidecars to S3, run CLI sync, populate table.
- **Phase 17** — frontend reads/writes the metadata-repository.
- **Phase 18** — full lifecycle: `_explicit_fields` pinning, Claude enrichment, approve/regenerate/edit.
